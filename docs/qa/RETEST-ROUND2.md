# Round 2 re-test: B-14 to B-22 and R-01 on Ubuntu, Debian and openSUSE

> **In short:** status: in progress (Ubuntu 24.04 and Debian 13 complete). Re-test of the second batch of fixes from [DISTRO-UBUNTU-2404.md](DISTRO-UBUNTU-2404.md) (B-14 to B-22) and [DISTRO-UBUNTU-2404-RETEST.md](DISTRO-UBUNTU-2404-RETEST.md) (R-01) on disposable guests with a live AirVPN account. New: N-01 (an upgrade from the published 0.1.3 while connected keeps the old networking helper until reboot, because the 0.1.3 broker has no idle restart) and N-02 (once, the GNOME session ended right after installing the package on a freshly booted guest, as already seen once in the first round).

GUI driven through QMP; shell over SSH, or the guest agent while Network Lock blocks the LAN. The saved account was put into the Secret Service with `secret-tool` over stdin. DNS leaks were checked with `tcpdump -i <nic> port 53` during `getent`/`dig` lookups; HTTPS reachability with `curl` over IPv4 and IPv6.

## New bugs

### N-01 Upgrade from the published 0.1.3 while connected keeps the old helper running until reboot — minor

- **Build:** REL → FIX, Ubuntu 24.04.
- **Repro:** REL installed, Connect (lock on), `sudo apt install ./FIX.deb`, Disconnect, wait.
- **Actual:** the helper file is replaced and needrestart now (correctly, R-01) defers the restart, but the running broker is the 0.1.3 binary, which has no "exit once idle after replacement" logic. It keeps serving from the deleted executable after Disconnect and new connections, until reboot or `systemctl restart wave-vpn-service`. In 0.1.3, needrestart's restart was what refreshed it. Upgrades from FIX onwards are fine (U2).
- **Impact:** one-time, for users who upgrade from 0.1.3 while connected; helper-side fixes (B-14, B-22 resolver handling) do not apply until reboot, and nothing tells the user.
- **Code:** `src/service.rs:206-208` relies on the running broker's idle check (`src/service.rs:443-466`), which 0.1.3 lacks; `packaging/scripts/postinstall.sh:10-17`.
- **Suggested fix:** when `service-install` replaces the helper while connected, arrange a restart of the broker after the session (for example a transient `systemd-run --on-active` unit that restarts `wave-vpn-service.service` once `/run/wave-vpn/recovery.json` is gone), or have the new GUI compare the broker version and restart it after Disconnect.
- **Evidence:** `u-r01-apt-probe-journal.txt`.

### N-02 GNOME session ended right after the package install on a freshly booted guest — needs investigation

- **Repro (1 of 1 here; also once in the first round with `e194e24`):** roll back to `clean-desktop`, start, as soon as the autologin session is up (boot still `starting`, `plymouth-quit-wait` pending) run `sudo apt install ./FIX.deb`.
- **Actual:** 0.6 s after postinst's `systemctl enable --now wave-vpn-service.socket`, systemd stopped `gdm.service`; the user session closed and the boot then finished (`Startup finished`). On Ubuntu `gdm.service` has `Conflicts=plymouth-quit.service`.
- **Controls (no Wave):** in the same boot window, `daemon-reload` twice plus a service start, and a dummy socket unit enabled with `enable --now` (`WantedBy=sockets.target`): GDM kept running. Installing after boot finished (`is-system-running` = `running`) never ended the session (4 installs on Ubuntu this round).
- **Impact:** an install or unattended upgrade in the first seconds after boot could log the user out. Not attributed with certainty to Wave.
- **Code:** `src/service.rs:237-238` (daemon-reload, enable --now) called from `packaging/scripts/postinstall.sh:14`.
- **Evidence:** `u-gdm-stop-trigger.txt`, `u-gdm-stop-before.txt`, `u-gdm-control.txt`, `u-gdm-control2.txt`.
